## 2026-07-30 — Calendar edit form broken on week/day views; all-day meetings rendering as timed blocks

Branch: `Work` · Commit: `58decd3`

### Reported symptoms

1. On **week** or **day** view, clicking **Update** / **Update All** / **Update
   Next** left the Book Room form unpopulated — the header read `Invalid Date`,
   and the console showed:

   ```
   POST /api/specialpermissions/meeting 500 (Internal Server Error)
   Error fetching meeting special users: Error: WHERE parameter "meeting_id"
     has invalid "undefined" value
       at ... GetAllForMeeting (controllers/specialPermissionsController.js:34)
   ```

   The same flow worked correctly on **month** view.

2. Some meetings understood to be **All Day** rendered in week/day view as a
   full-height block growing down the time grid (`12:00am – 11:45pm`) instead
   of sitting in the all-day row at the top of the column.

### Root cause 1 — timeGrid day-cell click handler hijacks the edit form

`dayCellDidMount` in `src/Views/Pages/Calendar/index.jsx` attaches a native
`click` listener to every day cell in `timeGridWeek` / `timeGridDay`:

```js
info.el.addEventListener("click", () => {
    const start = info.date;
    const end = new Date(start);
    end.setHours(23, 59, 59, 999);
    handleRangeSelect({ start, end, allDay: false });
});
```

In FullCalendar v6 timeGrid views the day column **is** a day cell — it is
rendered through `DayCellContainer` as `<td class="fc-timegrid-col">`
(`@fullcalendar/timegrid/internal.js`, `TimeCol.render`) — and the events are
rendered *inside* it, under `.fc-timegrid-col-events`.

So clicking a meeting dispatched **both** handlers on the same native click:

| handler | effect |
| --- | --- |
| `eventClick` → `handleEventSelect` | `setSelectedEvent(...)`, `setIsModalOpen(true)` |
| bubbled day-cell click → `handleRangeSelect` | `setSelectedRange({start, end, allDay, view})` |

`MeetingFourm` receives its meeting as:

```js
meeting={ selectedRange ? selectedRange : selectedEvent?.id
            ? selectedEvent?.extendedProps : selectedEvent }
```

`selectedRange` wins, so the edit form opened against a bare range object:

- no `id` → `GetSpecialPermissionsForMeeting({ id: undefined })` →
  `SpecialPermission.findAll({ where: { meeting_id: undefined } })` → Sequelize
  throws → **500**.
- no `start_time` → `new Date(undefined).toLocaleDateString()` → **`Invalid
  Date`** in the dialog header.

Month view (`dayGridMonth`) takes the other branch of `dayCellDidMount`, which
only adds the hover "+" icon and no click listener — which is exactly why the
flow worked there.

### Root cause 2 — `getTime()` from date-fns v2 returns `NaN` for strings

`src/Views/Pages/Calendar/MeetingForum.jsx` gated the "restore stored times"
branch on:

```js
if (getTime(meeting.start_time) && getTime(meeting.end_time)) { ... }
```

date-fns v2 (`2.30.0`, confirmed installed) does **not** accept string
arguments — `toDate()` warns and returns `new Date(NaN)`. `meeting.start_time`
arrives from the API as an ISO string, so this condition was **always false**.

Every edit therefore fell into the fallback:

```js
setEndTime("12:15 AM");
setStartTime("12:00 AM");
setAllDay(true);
```

Consequences:

- The **All Day** checkbox was always checked when editing, regardless of the
  stored `all_day` value — the form was not reporting the real state.
- The time selects were hidden (`{!allDay && ...}`), so real times were never
  visible or editable.
- Saving wrote `00:00 → 00:15` over the meeting's actual times.

The `if` branch was also independently broken: `getHours()` in
`CommonFunctions.js` returns `0` for midnight, producing `"00:00 AM"` — a value
that does not exist in the `times` option list built by `formatTime()`
(which maps hour `0` → `12`), so the MUI `Select` would have rendered empty.

### Root cause 3 — `all_day` dropped when a recurrence occurrence is materialised

Recurring occurrences are synthetic (`id: -1`, generated by
`CreateRepeatingMeetings`). Editing one hits `Update` in
`backend/controllers/meetingControler.js`, which takes the `Number(id) === -1`
branch and **creates a real row** from `tempNew`. That payload omitted
`all_day`, so the model default (`false`) applied and a recurring all-day
meeting was silently persisted as a timed one.

This matches the observed data: *Rogue Testing* (recurring daily) rendered as a
full-height timed block, while *Martin & Carruthers* (non-recurring) sat
correctly in the all-day row.

Verified **not** at fault along the way:

- `CreateRepeatingMeetings` spreads `meeting.toJSON()`, so `all_day` survives
  recurrence expansion.
- `GetAllUserCanSee` returns model instances untouched — `all_day` survives the
  listing endpoint.
- `handleEventUpdate` (drag/resize) sends `all_day` where the API reads
  `allDay`, but Sequelize's `Model#update` runs
  `_.omitBy(values, v => v === undefined)` (`model.js:2577`), so the field is
  skipped rather than nulled. Harmless — though it does mean drag/resize cannot
  change all-day status.

### Changes applied

| File | Change |
| --- | --- |
| `src/Views/Pages/Calendar/index.jsx` | Day-cell click handler returns early when the click originates on `.fc-event`, `.fc-more-popover`, or `.fc-timegrid-more-link` |
| `src/Views/Pages/Calendar/index.jsx` | `setSelectedRange(null)` in `handleEventSelect` and `handleUpdateEvent` |
| `src/Views/Pages/Calendar/MeetingForum.jsx` | Skip the special-permissions fetch when `meeting?.id == null` |
| `src/Views/Pages/Calendar/MeetingForum.jsx` | Parse stored times with `new Date()` and format via `formatTime()` so values match the dropdown options; removed the now-unused `getTime` / `getAmPm` imports |
| `backend/controllers/specialPermissionsController.js` | `GetAllForMeeting` validates the id — 400 for a missing id or missing `recurrence_id`, 404 for an unknown recurrence — instead of letting Sequelize 500 |
| `backend/controllers/meetingControler.js` | `Update`'s `id === -1` branch includes `all_day: allDay` in the created meeting |

### Verification status

- All four files parse cleanly (`node --check` for backend, `@babel/parser`
  with the `jsx` plugin for the frontend).
- **Not** exercised in a browser, and the database was not queried. The
  root-cause-3 conclusion is drawn from reading the code paths, not from
  observing stored `all_day` values.

### Follow-ups

- [ ] **Existing rows are not repaired by this fix.** Any meeting already
      stored with `all_day = 0` still renders as a timed block. The checkbox is
      now honest, so opening a meeting shows its true state; re-saving with
      All Day ticked moves it to the all-day row. Consider a one-off data fix
      for meetings stored as `00:00 → 23:45`.
- [ ] `Update`'s `id === -1` branch also drops `it_support` and
      `it_support_details`, so "Edit Current" on a recurring meeting loses an
      IT support request. Same class of bug as root cause 3; left unchanged to
      keep the fix scoped.
- [ ] The injected day-cell click handler still fires on plain clicks and
      overwrites FullCalendar's own `select` result, so dragging out a time
      range in week/day view collapses to the whole day and the form falls back
      to "now". Removing the listener in favour of FullCalendar's `select` /
      `dateClick` would fix it, but needs a browser check that single clicks
      still open the booking dialog.
- [ ] The day-cell listeners are never removed — `dayCellDidMount` adds one per
      cell mount with no matching `dayCellWillUnmount`.
